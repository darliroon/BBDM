# 推理速度优化：从 30s 到 1s 的路线与实测

> 问题：CBBDM 推理一张图 200 步需 30-40s，降到 50 步仍要 ~10s，目标 **~1s**。
> 本文记录瓶颈实测、概念速览、达标方案（PRF + 少步 ODE）、空间选择建议与后续路线。
> 相关文档：[PRF_GUIDE.md](PRF_GUIDE.md)（PRF 使用方法）、[PRF_vs_CBBDM.md](PRF_vs_CBBDM.md)（设计思想对照）。

## 1. 基础概念速览

### NFE（Number of Function Evaluations）
网络前向计算次数。**推理耗时 ≈ NFE × 单次前向耗时**，是比"步数"更通用的计量单位：

- CBBDM 200 步 = 200 NFE（开 CFG 则 400：每步各算一次有 C / 无 C）
- PRF euler×10 = 10 NFE；PRF heun×8 = 16 NFE（heun 每步算两次）

### bf16（bfloat16）
16 位浮点：指数位与 fp32 相同（8 位）、尾数只有 7 位。**数值范围与 fp32 一致（不溢出）、精度略低**。在 Ampere（3090）上用 Tensor Core 跑 bf16 矩阵乘约 2× 吞吐、显存减半。推理标准做法（SD/SD3 推理默认半精度），质量损失可忽略。配套：
- **TF32**：Ampere 的另一种硬件加速模式（fp32 运算走 Tensor Core）
- **torch.compile**：算子融合编译

## 2. 瓶颈实测

测试环境：RTX 3090，batch=1，256²，生产配置 UNet（553M 参数），脚本 `tests/bench_inference.py`。

| 手段 | ms/NFE | CBBDM 200 步 | CBBDM 50 步 |
|---|---|---|---|
| fp32（仓库现状） | ~93 | 18.5s | 4.6s |
| +TF32 | ~86 | 17.3s | 4.3s |
| +bf16 autocast | ~71 | 14.2s | 3.6s |
| +bf16+compile（最优组合） | ~67 | 13.4s | 3.4s |

**关键结论：纯工程加速（精度/编译）只有 ~1.4×，到不了 1s。** 这是计算受限问题——553M UNet 在 256² 上每步前向就要 ~67-93ms，步数不砍下来无解。而 CBBDM 是随机反向扩散过程，砍步数质量明显劣化（这也是扩散模型要靠蒸馏才能少步的原因）。

（注：现场 30-40s 比实测 18.5s 慢一倍，可能来自 GPU 共享、采样时保存中间图等额外开销，但结论不变。）

## 3. 达标方案：PRF 内核 + 少步 ODE（端到端实测）

PRF（Paired Rectified Flow，见 [PRF_GUIDE.md](PRF_GUIDE.md)）为少步推理而生：直线轨迹 + 确定性 ODE，速度场极简单（A==B 处 v≡0，容量只花在 gap）。bf16+compile 下的端到端实测：

| 配置 | NFE | 实测耗时/图 |
|---|---|---|
| PRF euler×20 | 20 | 1372 ms |
| **PRF euler×10（推荐）** | 10 | **693 ms** ✅ |
| PRF euler×5 | 5 | 351 ms |
| PRF heun×8 | 16 | 1108 ms |
| PRF heun×4 | 8 | 558 ms |

**PRF euler×10 ≈ 0.7s，达标**（同样 NFE 下 heun 精度更高：一阶 Euler 误差 O(dt)，二阶 Heun 误差 O(dt²)，本任务速度场简单，euler×10 已足够）。

配置方法（`model.BB.params`）：`gamma: 0.0`（直线最直，最适合少步）、`solver: 'euler'`、`sample_step: 10`。

CBBDM 也可叠加工程加速应急：TF32+bf16+compile 下 50 步从 ~10s 降到 ~3.4s。

## 4. 空间选择：纯像素 vs VQGAN 潜空间

**背景疑问**：纯像素 CBBDM 慢，是否应换 VQGAN 潜空间（LBBDM/LPRF）+ 输入端加网络层补偿细线损失？

**结论：保留纯像素 + PRF 少步，不建议 VQGAN 潜空间。**

1. **速度目标已达成，VQGAN 的收益用不上了。** 潜空间的全部意义是把 UNet 从 256² 搬到 64²（约 10× FLOPs 减少），那是 200 步扩散时代的刚需。PRF euler×10 = 0.7s 已在 1s 内，为不需要的速度引入细线丢失风险，不划算。

2. **"输入端加网络层"救不回 VQGAN 丢的信息。** 关键误区澄清：VQGAN 的信息损失发生在 **encoder 量化那一步**（每个 4×4 像素块映射到最近的 codebook 向量）。UNet 及其输入层只看得到 latent——2-3px 细线落在 4×4 网格里，预训练的 LDM VQGAN（自然图像 codebook）很可能把它量化抹掉。**信息在进入下游网络前就没了，下游加多少层都无法恢复。** 理论上可以设计像素级 skip 直连解码器的残差结构，但那是定制工程，复杂度远超收益。

3. **任务特性决定信号就是细线本身。** 车道线图 98% 是白底，有效信息全在 2-3px 的线上——压缩比与信号保真直接对立，而生成质量评估恰恰对线完整/断裂敏感。

**若将来要压到 <0.3s**（按性价比排序，全部留在像素空间）：

| 方案 | 预期 | 成本/风险 |
|---|---|---|
| Reflow（训好的 PRF 自采样 (A, B̂) 对再训一轮） | 1-2 步，~0.1s | 低；复用现有训练管线换数据源 |
| 缩小 UNet（`model_channels: 96` + 精简 channel_mult） | ~4× 提速 | 中；需重训对比（553M 对细线补全明显过参数化） |
| f2 自训 VQGAN（128² latent） | ~2-3× 提速 | 高；2×2 格子基本不丢 2-3px 线，但需自训 VQGAN 并验证重建，仅当上面两项不够时考虑 |

**若仍想验证隐空间可行性**（一次性实验，约半天）：用 B 图测 VQGAN 重建，算"线的像素召回"（重建图 vs 原图的线像素 IoU）。**>95% 才值得继续**，否则放弃。预训练 vq-f4 大概率过不了这一关——这也是 `Template-PRF-Latent-f4.yaml` 里预先写警告的原因。

## 5. 复现基准

```bash
cd /path/to/BBDM
python tests/bench_inference.py 0    # GPU id
```

脚本自动从 `configs/Template-{CBBDM,PRF}.yaml` 生成临时配置，加载 `results/lane_lines/{CBBDM,PRF}-pixel/checkpoint/latest_model_1.pth`（冒烟 checkpoint，只测速度不测质量）。换用自己的 checkpoint 时改脚本头部 `CKPT` 字典即可。

测量项：单次 UNet 前向（fp32 → TF32 → bf16 → +compile 逐级叠加）→ 各步数端到端投影 → PRF 端到端实测（euler/heun 多档步数）→ CBBDM 端到端实测对照。
